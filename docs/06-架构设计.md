# 架构设计

> 基于《架构整洁之道》的项目架构设计文档

---

## 一、为什么需要架构设计

一个文档网站看似简单，但随着内容增长、多语言扩展、团队协作深入，如果没有清晰的架构约束，很快会陷入"改一处崩三处"的泥潭。

《架构整洁之道》的核心思想是：**依赖关系必须指向内部，越靠近中心越稳定，越靠近外层越易变。**

我们把这一思想应用到 Docusaurus 文档站点上。

## 二、Clean Architecture 四层模型

```
┌─────────────────────────────────────────┐
│  Frameworks & Drivers                   │  ← Docusaurus, React, Node.js
│  (外层 — 最易变)                         │
│  docusaurus.config.ts                   │
├─────────────────────────────────────────┤
│  Interface Adapters                     │  ← React Components, Theme overrides
│  (适配层)                                │
│  src/components/, src/pages/            │
├─────────────────────────────────────────┤
│  Application Business Rules             │  ← Config, Routing, Navigation
│  (应用层)                                │
│  config/site.ts, config/navbar.ts...    │
├─────────────────────────────────────────┤
│  Enterprise Business Rules              │  ← Content, Data Models
│  (领域层 — 最稳定)                       │
│  docs/, blog/, i18n/                    │
└─────────────────────────────────────────┘
```

### 各层职责

| 层级 | 职责 | 变更频率 | 示例 |
|---|---|---|---|
| **领域层** (Entities) | 内容本身、数据结构 | 低 | Markdown 文档、翻译文件 |
| **应用层** (Use Cases) | 内容组织、导航、搜索配置 | 中 | 侧边栏、导航栏、站点元数据 |
| **适配层** (Interface Adapters) | UI 组件、页面布局 | 中 | React 组件、主题覆盖 |
| **框架层** (Frameworks) | 框架接入、构建配置 | 高 | docusaurus.config.ts |

## 三、项目目录结构

```
website/
├── content/                          # 领域层 — 纯内容
│   ├── docs/                        # 英文文档（默认语言）
│   ├── blog/                        # 英文博客
│   └── i18n/                        # 多语言翻译
│       └── zh-CN/
│           ├── code.json             # UI 字符串翻译
│           └── docusaurus-plugin-content-docs/
│               └── current/          # 中文文档镜像
│
├── config/                           # 应用层 — 配置逻辑
│   ├── site.ts                       # 站点元数据（标题、域名等）
│   ├── navbar.ts                     # 导航栏配置
│   ├── footer.ts                     # 页脚配置
│   ├── algolia.ts                    # 搜索配置
│   └── sidebars/                     # 按语言分离的侧边栏
│       ├── en.ts
│       └── zh-CN.ts
│
├── src/                              # 适配层 — React 组件
│   ├── components/
│   │   └── HomepageFeatures/        # 首页特性展示
│   ├── pages/
│   │   └── index.tsx                # 首页
│   └── css/
│       └── custom.css               # 自定义样式
│
├── static/                           # 静态资源
│   └── img/
│
└── docusaurus.config.ts              # 框架层 — 薄层接入
```

## 四、关键设计决策

### 决策 1：配置模块化

**问题**：`docusaurus.config.ts` 通常会膨胀成几百行的"上帝文件"。

**方案**：将 navbar、footer、site metadata、algolia 等配置拆分到 `config/` 目录下的独立 TypeScript 模块。

**收益**：
- 每个配置文件的职责单一
- 类型安全 — 导出的配置有明确的 TypeScript 类型
- 易于测试 — 纯函数/纯对象，无需启动 Docusaurus
- 框架无关 — `config/site.ts` 不 import 任何 Docusaurus API

### 决策 2：内容与配置分离

**问题**：Docusaurus 默认把 docs 和 sidebars 放同一层，容易混淆"内容"和"内容组织逻辑"。

**方案**：
- `docs/` 只放 Markdown 内容（领域层）
- `config/sidebars/` 放导航结构（应用层）
- 两者通过路径约定关联，而非硬编码耦合

### 决策 3：多语言的 Clean 处理

**问题**：多语言站点容易变成"复制粘贴地狱"——中英文文档各自独立维护，改一处要改两处。

**方案**：
- 默认语言（English）的文档放在 `docs/`，作为 Source of Truth
- 翻译文档放在 `i18n/[locale]/docusaurus-plugin-content-docs/current/`，镜像源文档结构
- 侧边栏配置也按语言分离：`config/sidebars/en.ts` 和 `config/sidebars/zh-CN.ts`
- UI 翻译通过 `code.json`、`navbar.json`、`footer.json` 统一管理

**未来优化方向**：
- 引入 Crowdin / Transifex 等翻译管理平台
- 用 Git 子模块或脚本自动同步源文档变更到翻译分支

### 决策 4：框架层保持"薄"

`docusaurus.config.ts` 的设计原则：

- **只 import，不定义**：所有业务配置都从 `config/` import
- **无逻辑**：不写 if/else、不写数据处理
- **可替换**：如果要迁移到 VitePress 或 Astro，只需重写这一个文件

```typescript
// docusaurus.config.ts — 理想状态
import {siteConfig} from './config/site';
import {navbarConfig} from './config/navbar';
import {footerConfig} from './config/footer';

export default {
  title: siteConfig.title,
  navbar: navbarConfig,
  footer: footerConfig,
  // ... Docusaurus-specific wiring only
};
```

## 五、多语言路由策略

| 访问地址 | 语言 | 内容来源 |
|---|---|---|
| `zerolang.app/docs/intro` | English (默认) | `docs/intro.md` |
| `zerolang.app/zh-CN/docs/intro` | 简体中文 | `i18n/zh-CN/.../intro.md` |

### 为什么选择子路径而非子域名？

| 方案 | 示例 | 优点 | 缺点 |
|---|---|---|---|
| **子路径** (推荐) | `/zh-CN/docs` | SEO 集中、部署简单、Cookie/Session 共享 | URL 稍长 |
| 子域名 | `zh.zerolang.app` | URL 简洁 | 需多站点部署、SEO 分散、配置复杂 |
| 独立域名 | `zerolang.cn` | 完全独立 | 维护成本高、内容同步困难 |

**结论**：子路径方案在 Docusaurus 中有原生支持，部署零额外成本，是最佳起点。

## 六、扩展性设计

### 添加新语言

```bash
# 1. 添加 locale 配置
docusaurus.config.ts → i18n.locales.push('ja')

# 2. 创建侧边栏配置
config/sidebars/ja.ts

# 3. 生成 UI 翻译模板
npm run write-translations -- --locale ja

# 4. 翻译内容
mkdir -p i18n/ja/docusaurus-plugin-content-docs/current/
# 复制并翻译文档
```

### 添加新文档分类

```bash
# 1. 在 docs/ 下创建新目录
docs/advanced/

# 2. 在 config/sidebars/en.ts 添加导航项

# 3. 在 config/sidebars/zh-CN.ts 添加对应项

# 4. 在 i18n/zh-CN/... 下创建翻译版本
```

## 七、与《架构整洁之道》的对应

| Clean Architecture 概念 | 本项目中的体现 |
|---|---|
| **Entities** | `docs/`、`blog/`、翻译内容 — 最稳定的业务知识 |
| **Use Cases** | `config/sidebars/`、内容组织逻辑 — 应用规则 |
| **Interface Adapters** | `src/components/`、React 页面 — 框架适配 |
| **Frameworks & Drivers** | `docusaurus.config.ts`、Docusaurus 本身 — 外层细节 |
| **Dependency Rule** | `config/site.ts` 不 import Docusaurus；`docusaurus.config.ts` import `config/site.ts` |
| **The Database Is a Detail** | Markdown 文件就是"数据库"，可以被任何工具读取 |
| **The Web Is a Detail** | 内容写在 Markdown 里，不绑定任何前端框架 |
